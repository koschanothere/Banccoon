# Banccoon Development Phases

Banccoon is a private, offline-first financial forecasting desktop app. The foundation is now mostly in place: local SQLite data, forecasting, recurrence, import/export, statement parsing, category learning, reconciliation services, savings goals, credit-card projections, and a first MAUI desktop UI are already present.

The roadmap now shifts from “build the primitives” to “make the app guide the user through real financial workflows.”

## Completed Foundation

- Solution split into Core, Infrastructure, App, and Tests.
- Domain models for accounts, categories, transactions, scheduled transactions, savings goals, settings, recurrence, statement imports, reconciliation, and credit-card details.
- Forecasting and recurrence services with test coverage.
- Local SQLite repositories for saved financial data.
- JSON backup/export, validation, merge/replace import, and guarded local-data reset.
- Desktop shell with dashboard, accounts, transactions, statements, scheduled items, goals, forecast, reconciliation, analytics, data, and preferences surfaces.
- Savings-goal reservations and credit-card payoff/obligation calculations.
- Bank statement import foundation with parser registry, Sberbank debit-card parser, pending import batches/rows, duplicate warnings, category suggestions, local category learning, and row approve/skip.
- Basic reconciliation/check-in services and UI for expected scheduled items, actual balance comparison, grouped spending, and balance adjustments.
- Dashboard account-total controls and projected-balance chart.

## Current Product Direction

The app should no longer assume users manually build everything first. On first startup (empty db), Banccoon should guide the user into setup through a focused in-app overlay. The first useful setup paths should be bank-statement import, manual setup, and backup restore from exports.

Large workflows should become app-guided experiences rather than permanent top-level tabs: quick edits are modal overlays, but multi-step flows (statement import, reconciliation) are dedicated full pages, not modals. See `docs/ui-structure-decisions.md` for the full structural spec — it is the source of truth for information architecture and interaction patterns; this file governs implementation phasing only.

The dashboard's headline number is a **"Free to spend" figure** built on the existing `AvailableToSpendService`, extended with a user-set safety-buffer reserve and selectable window modes (rolling days / calendar-aligned / dynamic-until-next-major-payment) — see "Money Model: Free to Spend" in `docs/ui-structure-decisions.md` for the full spec. Not yet assigned to a specific phase below; fold into dashboard-rework phasing when that work is scheduled.

- **Fixed a real, app-breaking crash — root-caused via bisection, not guessing**: the app crashed on every single launch with an identical native `STATUS_STOWED_EXCEPTION` (`0xC000027B`, identical fault offset every time) inside `Microsoft.ui.xaml.dll`. This is a native crash below the managed exception layer — nothing printed to console even when temporarily switching `OutputType` from `WinExe` to `Exe`; it only surfaced via Windows Event Viewer (Windows Logs → Application). Two plausible-looking hypotheses were tried and **disproven by actually testing them** (removing `window.SystemBackdrop = null`; reverting the chart's `PointerGestureRecognizer`) — both left the identical crash unchanged, which should have been the signal to stop guessing sooner. Real `git checkout` bisection across the session's commits (`d80188a` launches fine → `bac9b37` crashes) narrowed it to one commit, and its diff showed the actual cause: `App`'s constructor was changed to take `AppShell` as a constructor-injected dependency, and `AppShell` in turn took `AppShellViewModel` — chaining a UI/Shell object as a DI dependency of `Application` itself. Constructor-injecting *services* into `App` is standard, documented MAUI; constructor-injecting *another page/Shell object* into `App` at that same early bootstrap point is not, and native-crashes deterministically. Fixed by reverting `App`/`AppShell` to the standard `MainPage = new AppShell()` pattern, with `AppShell`'s parameterless constructor resolving `AppShellViewModel` via the service locator (`IPlatformApplication.Current!.Services.GetRequiredService<AppShellViewModel>()`) instead of constructor injection — keeps the favorites-sidebar feature working without the unsafe DI chain. **Lesson for later**: don't constructor-inject `AppShell`/other `Page`/`Shell` types into `App`; use the service locator from within their own parameterless constructors instead. Also: when a fix doesn't change a deterministic crash's exact fault offset, that's a strong signal the hypothesis is wrong — verify before declaring victory, don't just report the plausible-sounding theory as fixed.

- **Sidebar bug: root-caused via the diagnostics log, not guessed.** User reported the sidebar occasionally goes visually blank after continued use (flyout items disappear, stay clickable, don't navigate) — not a crash. First hypothesis (SQLite schema-init running on every repository call, not once per app lifetime) was fixed regardless since it was a real problem, but the user confirmed the bug still happened with that fix in place. The diagnostics added right after (`DiagnosticLog` → `%LOCALAPPDATA%\Banccoon\diagnostics.log`, via `AppDomain.UnhandledException`/`TaskScheduler.UnobservedTaskException`/WinUI's own `Application.UnhandledException`) then caught the real cause on the next occurrence: `System.Runtime.InteropServices.COMException (0x8000FFFF)` — `E_UNEXPECTED` — logged from WinUI's own unhandled-exception hook, while the user was "just switching tabs / opening and closing menus."
  - **Root cause**: `Microsoft.Data.Sqlite`'s async methods use `ConfigureAwait(false)` internally, so code after `await someRepository.GetXAsync()` can resume on a thread-pool thread instead of the UI thread. Several ViewModels then mutated an `ObservableCollection` bound to a live `CollectionView`/`Picker` (`.Clear()` + `.Add()` in a loop) directly after such an await — mutating UI-bound state from off the UI thread is illegal in WinUI and throws exactly this class of native COM exception. The sidebar's `AppShellViewModel.RefreshFavoritesAsync` was the prime suspect since it fires unconditionally on *every* Shell navigation (i.e. every tab switch), but the same pattern existed in every other ViewModel that rebuilds a collection after an await.
  - **Fix**: added `ViewModelBase.RunOnMainThreadAsync(Action)` (wraps `MainThread.InvokeOnMainThreadAsync`) and routed every UI-collection mutation that follows an `await` through it — `AppShellViewModel.RefreshFavoritesAsync`, `ResolveUpcomingListViewModel.RefreshAsync`, `TransactionsViewModel.InitializeAsync` (`RebuildOptionLists`/`ApplyFilters`), `ScheduleFormViewModel.OpenInternalAsync`, `CategoryManagementViewModel.RefreshAsync`, `NewTransactionFormViewModel.OpenAsync`, `AccountsViewModel.InitializeAsync`, `DashboardViewModel.LoadChartAsync`. Synchronous call sites already on the UI thread (e.g. property setters triggered by a button click) were left as direct calls — only the post-await call sites needed wrapping.
  - Not yet swept (at the time): plain scalar property setters after an await (e.g. `IsLoading = false` in several `finally` blocks) — flagged as lower-probability but real residual risk.

- **High-priority backlog: bank parser coverage.** Sberbank exists. Tinkoff and Alphabank are next, confirmed must-have — each needs a real statement sample from an actual account holder before the parser can be built/verified.
- **Sberbank parser redo, step 1 done: real bugs found and fixed against a real statement, not the synthetic test fixtures.** A real 2-page statement was fed through the actual `ExtractLines`/`ParseExtractedLines` pipeline (not a generic PDF-to-text dump) and every line annotated against what the parser did with it — see the "Statement Parser Playground" artifact from that session for the full line-by-line breakdown. Found and fixed:
  - **Page-boundary corruption (high impact, confirmed on 2 of 19 real transactions)**: the parser had no concept of "end of the operations table" — any line that wasn't an operation, a description continuation, or on a growing ignore-prefix list got silently appended to whichever transaction was still pending. On the real statement this glued the page-break's QR-code instructions onto the last transaction before the break, and the certificate/signature legal text onto the very last transaction in the document. Fixed by flushing the pending row whenever a table-boundary marker appears (`ДАТА ОПЕРАЦИИ` repeating, `Продолжение`, or `Дата формирования`) instead of relying on an ignore-list — this let the entire old `ShouldIgnoreLine` blocklist be deleted, since content outside an active pending operation is now unconditionally skipped regardless of what it says.
  - **Account number no longer guessed** — previously a heuristic (any 16-34 digit run on a line with no period and no card mask). Now anchored on the literal "Номер счёта" label, matching the user's explicit request to stop depending on the (also mojibake-broken) "Карта" keyword.
  - **Per-operation running balance was parsed by regex and then discarded.** Added `ParsedStatementRow.BalanceAfter`; `ClosingBalance` is now the most recent operation's own balance, not the header's "Остаток на \<date\>" summary line — confirmed on the real statement these actually disagree (16,971.91 from the last operation vs. 20,671.91 stated in the header), validating the user's call not to trust the header figure.
  - Removed the dead, mojibake-garbled `"Карта"` keyword check in card-last-four detection (it never matched anything real; the regex-based `••••`-mask fallback was doing all the actual work). The same mojibake existed in the test fixtures themselves and has been corrected there too, along with fixing the fixtures' operation order (was oldest-first; real Sberbank statements print newest-first).
- **Step 2 done: recipient-based type memory, not just category memory.** `CategoryLearningRule` already stored a `Type` per rule but only as an input filter — nothing suggested type itself, so every row was stuck with the parser's raw +/- sign guess forever, and a `"Перевод"`-labelled operation (ambiguous: could be a real transfer, or an expense/income to a third party the bank just calls a "transfer") could never be corrected in a way the app would remember.
  - New `ICategorySuggestionService.SuggestType` scans learning rules for the same recipient **across all types** (unlike `Suggest`, which is scoped to one type) and returns whichever type has the strongest match — letting a past correction override the raw sign-based guess before category suggestion runs.
  - `ApproveRowAsync` now takes an optional `type` override, and the review row template has an Expense/Income toggle (mirrors the existing `ScheduleFormViewModel` pattern) so a wrong guess can be corrected before approval — that correction is exactly what trains `SuggestType` for next time, since the approved row's final type is what gets learned.
  - Recipient text is now trimmed to its "core name" before matching/learning (truncated at the first purely-numeric token), so `PYATEROCHKA 25673 MOSCOW RUS` and `PYATEROCHKA 30142 SPB RUS` are recognized as the same recipient instead of needing to be learned separately per store number.
- **Step 3 done: Transfer support end-to-end, including the cross-account case.**
  - Review rows can now be marked Transfer (a third toggle next to Expense/Income), which reveals an "other account" picker populated from every other tracked account. Choosing one and approving learns the (recipient → destination account) mapping via a new `CategoryLearningRule.DestinationAccountId`, and `ICategorySuggestionService.SuggestDestinationAccount` pre-fills it next time the same recipient shows up — same shape as category/type learning, reusing the same scoring.
  - **A real correctness bug caught before it shipped**: the batch's own account isn't always the Transfer's source. A row that arrived as money *coming in* (the original statement's own +/- sign — captured as `StatementImportRow.IsIncoming`, independent of whatever Type the row gets reclassified to, since "Transfer" alone doesn't say which way money moved) needs the importing account as the *destination* and the picked account as the *source* — otherwise both balances would move backwards. `ApproveRowAsync` now resolves source/destination roles from `IsIncoming` rather than always assuming the batch's account is the source, and creates the transaction via `ITransactionApplicationService.ApplyNewTransaction` (which already correctly credits both sides) instead of the single-account balance updater used everywhere else in this service.
  - **Cross-account duplicate detection**: approving a Transfer from account A's statement (crediting B) previously left account B's own future statement import blind to it — `GetByAccountIdAsync` only ever matched `WHERE AccountId = @AccountId`, never `DestinationAccountId`, so the transfer's destination side was invisible to any duplicate check run from B's perspective. Fixed by broadening that query (its only caller is this exact duplicate check) and adding a second duplicate-match path: a Transfer already recorded with this account as its destination counts as the same event even when the two statements describe it completely differently — date, close-enough time, and amount are the only signal that can be trusted across two independently-worded bank statements. This needed `Time` to actually exist on `ParsedStatementRow`/`StatementImportRow`/`Transaction` at all (parsed by regex, same as the balance was, and previously discarded the same way).
  - **A real bug caught by the new tests, not by inspection**: `TimeOnly`'s own `-` operator wraps to stay non-negative (`10:00 - 10:02` comes back as ~23h58m, not −2m), which silently broke the "within 5 minutes" tolerance check entirely - it would never have matched two real times that were merely minutes apart. Fixed by computing the difference from each side's minute-of-day instead of using the operator, with a midnight-wraparound case handled explicitly. Caught by `ApproveRowAsync_...Transfer` / `CreatePendingImportAsync_FlagsTransferAlreadyRecordedFromTheOtherAccountAsDuplicate` in `StatementImportServiceTests` — worth remembering as a general caution about `TimeOnly`/`DateOnly` arithmetic operators in this codebase.
  - Transfers now get a category too (changed per direct instruction) — the earlier "Transfer is category-exempt" logic is gone from `ApproveRowAsync`, so `CategoryLearningRule.CategoryId` didn't need to become nullable and no destructive schema migration was needed for it, only new additive nullable columns (`Time` on `Transactions`/`StatementImportRows`, `DestinationAccountId` on `StatementImportRows`/`CategoryLearningRules`, `IsIncoming` on `StatementImportRows`) via the usual `AddMissingColumnAsync` pattern.
  - `StatementImportService.cs` had grown to 510 lines with all of the above; the duplicate-detection logic (`FindDuplicate` and its three pure-function helpers) was pulled out into its own `StatementDuplicateDetector.cs` since it doesn't touch any instance state - down to 442 lines.

  - **Does not retroactively fix an account balance from an import that already completed** before this landed - the statement's closing balance was never persisted anywhere before now, so there's nothing to recover for those. A one-time manual correction via Accounts -> Edit -> Balance is needed for those accounts.

A `RowCountText` caption ("Showing 20 of 143") makes it clear more exist rather than looking like data went missing.

This means the header/filters stay put while paging through transactions, and a "load more" append doesn't shift the user's scroll position. Only checked by building + a clean launch, not by driving the actual UI (no tool available for that here) — worth a manual look, especially with the Add/Schedule form panels open on a shorter window, to confirm the 480px cap doesn't feel cramped in practice.
