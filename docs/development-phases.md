# Banccoon Development Phases

Banccoon is a private, offline-first financial forecasting desktop app. The foundation is now mostly in place: local SQLite data, forecasting, recurrence, import/export, statement parsing, category learning, reconciliation services, savings goals, credit-card projections, and a first MAUI desktop UI are already present.

The roadmap now shifts from “build the primitives” to “make the app guide the user through real financial workflows.”

## Current Product Direction

The app should no longer assume users manually build everything first. On first startup (empty db), Banccoon should guide the user into setup through a focused in-app overlay. The first useful setup paths should be bank-statement import, manual setup, and backup restore from exports.

Large workflows should become app-guided experiences rather than permanent top-level tabs: quick edits are modal overlays, but multi-step flows (statement import, reconciliation) are dedicated full pages, not modals. See `docs/ui-structure-decisions.md` for the full structural spec — it is the source of truth for information architecture and interaction patterns; this file governs implementation phasing only.

The dashboard's headline number is a **"Free to spend" figure** built on the existing `AvailableToSpendService`, extended with a user-set safety-buffer reserve and selectable window modes (rolling days / calendar-aligned / dynamic-until-next-major-payment) — see "Money Model: Free to Spend" in `docs/ui-structure-decisions.md` for the full spec. Not yet assigned to a specific phase below; fold into dashboard-rework phasing when that work is scheduled.

This is a native crash below the managed exception layer — nothing printed to console even when temporarily switching `OutputType` from `WinExe` to `Exe`; it only surfaced via Windows Event Viewer (Windows Logs → Application). Two plausible-looking hypotheses were tried and **disproven by actually testing them** (removing `window.SystemBackdrop = null`; reverting the chart's `PointerGestureRecognizer`) — both left the identical crash unchanged, which should have been the signal to stop guessing sooner. Real `git checkout` bisection across the session's commits (`d80188a` launches fine → `bac9b37` crashes) narrowed it to one commit, and its diff showed the actual cause: `App`'s constructor was changed to take `AppShell` as a constructor-injected dependency, and `AppShell` in turn took `AppShellViewModel` — chaining a UI/Shell object as a DI dependency of `Application` itself. Also: when a fix doesn't change a deterministic crash's exact fault offset, that's a strong signal the hypothesis is wrong — verify before declaring victory, don't just report the plausible-sounding theory as fixed.

- **Sidebar bug: root-caused via the diagnostics log, not guessed.** User reported the sidebar occasionally goes visually blank after continued use (flyout items disappear, stay clickable, don't navigate) — not a crash. First hypothesis (SQLite schema-init running on every repository call, not once per app lifetime) was fixed regardless since it was a real problem, but the user confirmed the bug still happened with that fix in place. The diagnostics added right after (`DiagnosticLog` → `%LOCALAPPDATA%\Banccoon\diagnostics.log`, via `AppDomain.UnhandledException`/`TaskScheduler.UnobservedTaskException`/WinUI's own `Application.UnhandledException`) then caught the real cause on the next occurrence: `System.Runtime.InteropServices.COMException (0x8000FFFF)` — `E_UNEXPECTED` — logged from WinUI's own unhandled-exception hook, while the user was "just switching tabs / opening and closing menus."
  - **Root cause**: `Microsoft.Data.Sqlite`'s async methods use `ConfigureAwait(false)` internally, so code after `await someRepository.GetXAsync()` can resume on a thread-pool thread instead of the UI thread. Several ViewModels then mutated an `ObservableCollection` bound to a live `CollectionView`/`Picker` (`.Clear()` + `.Add()` in a loop) directly after such an await — mutating UI-bound state from off the UI thread is illegal in WinUI and throws exactly this class of native COM exception. The sidebar's `AppShellViewModel.RefreshFavoritesAsync` was the prime suspect since it fires unconditionally on *every* Shell navigation (i.e. every tab switch), but the same pattern existed in every other ViewModel that rebuilds a collection after an await.
  - **Fix**: added `ViewModelBase.RunOnMainThreadAsync(Action)` (wraps `MainThread.InvokeOnMainThreadAsync`) and routed every UI-collection mutation that follows an `await` through it — `AppShellViewModel.RefreshFavoritesAsync`, `ResolveUpcomingListViewModel.RefreshAsync`, `TransactionsViewModel.InitializeAsync` (`RebuildOptionLists`/`ApplyFilters`), `ScheduleFormViewModel.OpenInternalAsync`, `CategoryManagementViewModel.RefreshAsync`, `NewTransactionFormViewModel.OpenAsync`, `AccountsViewModel.InitializeAsync`, `DashboardViewModel.LoadChartAsync`. Synchronous call sites already on the UI thread (e.g. property setters triggered by a button click) were left as direct calls — only the post-await call sites needed wrapping.

## i18n (English + Russian, extensible to more later) — running log, complete except default-category names

Full end-to-end i18n for the app's own UI — mechanism, remaining Core cleanup, the full string/translation sweep, and wiring it into Settings. Follows on from the language-control backlog item first raised in Implementation Progress below ("the app currently has no language/locale setting at all"). This is a big, multi-session job; tracked here as a running log so partial progress across sessions stays legible instead of restarting the scoping each time.

**Decisions (do not re-litigate):**

1. **Mechanism**: resx-backed storage, exposed through a static ambient `Translator` class (implementing `INotifyPropertyChanged` so bindings re-evaluate on language change), plus a `{loc:Translate Key}` XAML markup extension. Not `IStringLocalizer<T>` DI injection — this codebase's idiom for cross-cutting, no-DI state is a plain static class (`Banccoon.App.Formatting.PrivacyMode`, the theme converters reading `Application.Current.RequestedTheme` directly). Follow that shape rather than reaching for DI injection into Page/ViewModel constructors, which would be a much bigger, riskier blast radius for no benefit here.
2. **Live switching, not restart-required.** Theme already switches live via `AppThemeBinding` (`SettingsViewModel.ApplyTheme`) — language gets the same immediacy via the Translator's own change-notification, since retrofitting live-switch onto a restart-only mechanism later would mean redoing the binding plumbing for every key a second time.
3. **Core must stop returning pre-composed English sentences.** Two spots needed this treatment: `RecurrenceDescriptionService` (done first, template for the rest) and `AnalyticsService.BuildTrend`'s `"Uncategorized"` literal (done). `BalanceAdjustmentService`'s `$"Balance adjustment {direction}"` Notes-column text is explicitly left as-is — frozen at creation time, same treatment already given to Russian bank-statement text; not a display-time formatting concern.
4. **Sequencing**: foundation (Translator/resx infra + the Core fixes) first, then Settings wiring, then the full 8-screen XAML string-literal retrofit as one deliberate global pass — same "don't chase it screen-by-screen" precedent as the icon pass in `docs/visual-design-language.md` — rather than blocking on a full sweep before anything is usable. Any new screen built after the foundation lands must use the Translator/key pattern from day one, not raw strings.
5. **Explicitly out of scope for this whole effort**: bank-statement parsing / category-learning text (naturally Russian regardless of UI language — a data concern, not a UI-translation concern; do not touch `Banccoon.Core.Statements`), and default-category-name localization (separate, later backlog item — the Translator/key foundation should extend to it cleanly, but it isn't being built now).

**Remaining work, roughly in order:** Translator + resx scaffolding (`Banccoon.App.Localization`, static `Translator.Get(key)`, `INotifyPropertyChanged`, culture switching) → `{loc:Translate Key}` XAML markup extension → wire `GeneralPreferencesViewModel`'s `SelectedLanguage`/`AppSettings.DisplayLanguage` to actually flip the culture live (same immediacy as `SettingsViewModel.ApplyTheme`) → enum-derived display text audit (`Banccoon.App.Formatting.DisplayText.Format` / `Banccoon.App.Converters.EnumDisplayConverter` split PascalCase enum names into labels — invisible to a plain XAML grep; ~8-10 of the 22 Core enums are actually user-facing) → the one canvas-drawn string (`ForecastChartView.Draw()`'s `canvas.DrawString("Today", ...)`) → real pluralization (English 2-form, Russian 3-form 1/21/31 vs 2-4/22-24 vs 0/5-20) fixing the 4 known manual-pluralization sites (`CategoryLearningRuleRowViewModel`, `DataManagementViewModel`, `TransactionsViewModel`, `StatementImportReviewViewModel`) → the actual translation sweep, ~300-450 XAML string literals across 8 screens (`AccountsPage`, `AppLockPage`, `DashboardPage`, `SettingsPage` — densest, ~103 literals — `StatementImportPage`, `TransactionsPage`, `AppShell`, `RecurrenceEditorView`) plus ~40 ViewModels' validation/status text, one screen per commit → the `ForecastChartView.cs` `CultureInfo.CurrentCulture` vs `InvariantCulture` axis-label inconsistency (~line 231; `MoneyFormat`/`DateDisplay`'s deliberate Invariant usage elsewhere is out of scope) → `AccountNumberFormat.Mask`'s hardcoded `"hidden"` fallback once the Translator exists.
